## Context

Consumer onboarding was an eleven-step manual guide: author `.project-narrative.json`, a preamble, two workflows, and a PR template by hand, then toggle repository settings. That copy-paste wall is high for humans, and in practice adopters install the processor by telling a coding agent *"add jamiemitchellconsultants/narrative to this repo."* Those agents had to reverse-engineer intent from a README aimed at humans and from `AGENTS.md`, which governs developing the processor rather than installing it — so results varied by tool.

## Decision

Add a non-destructive `narrative install` CLI command that scaffolds everything `init` does plus the maintenance and validation workflows and the PR template, refusing to overwrite any existing file and reporting the manual follow-ups it cannot perform. Ship `INSTALL.md` written for the installing agent as the authoritative consumer-install recipe, kept distinct from `AGENTS.md`. The action reference and required label live in single constants so a future release tag is a one-line repoint. Rejected: baking the workflows into `init` (would conflate the file-scaffolding primitive with full integration), and generating install content from a model (violates the deterministic, model-free contract).

## Consequences

Adoption becomes one command plus three surfaced admin toggles, and agent-driven installs become deterministic across tools. The scaffolded workflows still reference `@main`; when a `v1` release is cut, `ACTION_REF` and the workflows must be repointed to the pinned tag. `narrative install` is now a public interface and must stay non-destructive; changes to it require tests. INSTALL.md must be kept in sync with the scaffold set. Repository-settings toggles and label creation remain out of scope for the CLI by design and are reported for a human to complete.
